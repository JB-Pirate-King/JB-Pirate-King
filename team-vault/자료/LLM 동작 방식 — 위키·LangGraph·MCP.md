# LLM 동작 방식 — 위키·LangGraph·MCP

> "ChatGPT한테 물어봤어요"와 우리가 뭐가 다른가. **단순 챗봇 ≠ 시스템에 내장된 LLM.**
> Obsidian 동일본: `운영/11 LLM 동작 방식 - 위키·랭그래프·MCP`

## 0. 한 줄 요약
우리는 LLM을 **대화창에서 쓰지 않는다.** LLM을 **파이프라인의 부품**으로, **도구를 직접 쥐고(MCP)**, **상태기계 안에서(LangGraph)**, **검증 가능한 지식베이스(위키)** 위에서 돌린다. 즉 **"질문→답변" 챗봇이 아니라 "관측→판단→행동→기록"하는 자율 작업자**다.

---


## 1. 단순 챗봇 LLM vs 우리 방식 (핵심 차별점)
| 구분 | 단순 챗봇 (ChatGPT 대화) | 우리 프로젝트 |
| **입력** | 사람이 매번 프롬프트 타이핑 | 파이프라인 상태·로그·시트·git이 자동으로 LLM에 주입 |
| **출력** | 사람이 읽는 텍스트 | 구조화 JSON verdict → 다음 동작을 코드가 분기 |
| **도구** | 없음 (말만 함) | MCP로 git·Slack·Sheets·Notion·파일을 직접 조작 |
| **기억** | 세션 끝나면 소멸 | 위키(team-vault)·Obsidian·체크포인트에 영속 |
| **검증** | 사람이 눈으로 | 정량 게이트(+3.0pp)·더미 실행·LLM-as-judge로 자동 검증 |
| **반복** | 1회성 Q&A | LangGraph 사이클로 수렴까지 자동 반복 |
> 차별점의 본질: **LLM이 "조언자"가 아니라 "행위자(agent)"**다. 말하는 데서 끝나지 않고 도구를 쥐고 결과를 만들고 그걸 기록한다.

---


## 2. 세 기둥

### (1) LLM 위키 — "검증 가능한 지식 기반"
- **무엇**: 노션 SSOT → git(`team-vault/`) → 팀원 Obsidian으로 매일 자동 미러되는 단방향 지식베이스. PDF/DOCX는 markdown으로 자동 변환.
- **왜 LLM 위키인가**: 단순 문서 저장소가 아니라 **LLM이 읽고 쓰는 컨텍스트 원천**. `CLAUDE.md`, 운영 노트, 변환된 논문·자료를 LLM이 작업 시작 시 읽고 프로젝트를 즉시 파악.
- 사람과 LLM이 **같은 진실(SSOT)**을 본다 → "LLM이 옛날 정보로 헛소리"하는 문제를 구조적으로 차단.
- **챗봇과 차이**: 챗봇은 매번 백지에서 시작. 우리 LLM은 **프로젝트 기억을 들고** 시작한다.

### (2) LangGraph — "LLM을 상태기계로"
- **무엇**: 파이프라인을 **노드(작업)+엣지(흐름)의 그래프**(StateGraph)로 표현. 분기·사이클·중단/재개가 가능한 제어구조.
- **개념**: 노드(작업 단위, State 받아 갱신) / 조건엣지(`verdict`에 따라 분기) / 사이클(브랜치 체이닝 = 자동 반복) / `interrupt()`(멈췄다 사람 승인받고 재개, HITL) / 체크포인터(상태 저장 → 재개).
- **왜 중요**: 챗봇은 "한 번 묻고 한 번 답"이지만, LangGraph는 **여러 LLM 호출을 흐름으로 엮어** "분석→판단→재시도→사람승인→반복"을 **하나의 프로그램**으로 만든다.
- **우리 적용처**: ① ML 오케스트레이터(heahgo) ② 야간 운영봇 `ops_graph.py` — 6개 헬스체크 노드 병렬 → 집계 → 조건분기(경보/요약).

### (3) MCP (Model Context Protocol) — "LLM에게 손을 달아주기"
- **무엇**: LLM이 외부 도구/서비스를 **표준 규약으로 직접 호출**하게 하는 프로토콜. 텍스트만 뱉는 게 아니라 함수를 부른다.
- **우리가 붙인 MCP**: GitHub, Google Sheets, Notion, Slack, Obsidian, 파일시스템, 시퀀셜씽킹 등.
- **왜 중요**: MCP가 있어야 LLM이 **"~하세요"라고 말하는 대신 직접 ~한다.** 시트에 결과를 쓰고, git 브랜치를 만들고, 노션 페이지를 발행하고, Slack에 보고하는 걸 사람 손 없이.
- **챗봇과 차이**: 챗봇은 "이 명령어를 실행하세요" 안내. MCP 에이전트는 **그 명령을 자기가 실행**하고 결과를 확인한다.

## 3. 셋이 합쳐지면 (실제 동작)

```javascript
[위키/SSOT]  ──읽기──▶  [LangGraph 노드: LLM 호출]  ──MCP──▶  [git/Sheets/Slack/Notion 조작]
     ▲                          │ verdict(JSON)                      │
     │                          ▼ 조건분기                            │
     └────────────────  [결과를 위키·시트에 기록] ◀───────────────────┘
                         (다음 LLM 호출의 컨텍스트가 됨 = 학습 루프)
```

1. LLM이 **위키/상태**를 읽어 맥락 파악 (백지 아님)
1. **LangGraph 노드** 안에서 분석·판단 → 구조화된 결정(continue/retry/stop)
1. **MCP**로 실제 행동(브랜치 생성·시트 기록·Slack 보고·배포)
1. 결과를 **위키/시트에 기록** → 다음 사이클의 입력 → **자가개선 루프**
단순 챗봇은 1·2의 일부(텍스트 답변)만 하고 3·4가 없다.
