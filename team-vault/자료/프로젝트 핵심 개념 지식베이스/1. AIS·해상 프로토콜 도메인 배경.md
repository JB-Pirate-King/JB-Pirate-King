# 1. AIS·해상 프로토콜 도메인 배경

## 한눈에 보는 데이터 흐름
우리 IDS가 다루는 데이터(AIS)는 다음 경로로 흐른다. 각 단계가 별도의 개념·공격면(attack surface)이 된다.

```javascript
선박 센서(GPS/자이로/속도계)
   → AIS 트랜스폰더 (VHF로 broadcast, 평문·무인증)
   → NMEA 0183 ASCII 문장으로 표현 (AIVDM 캡슐화)
   → ECDIS / ECS / OpenCPN 에서 디코딩·표시
   → (여기서 IDS가 AIS 필드 시계열을 보고 이상탐지)
```

- **물리 계층**: AIS는 VHF(초단파) 무선으로 one-to-many **broadcast**.
- **데이터 표현 계층**: 내부 binary → **NMEA 0183 ASCII 문장**(AIVDM)으로 변환.
- **표시·통합 계층**: ECDIS/ECS/OpenCPN이 다양한 센서를 통합해 해도 위에 표시.
- → 우리 IDS는 AIS 메시지에서 추출된 필드(SOG, COG, Heading, 위치 등)의 **시계열 패턴**을 보고 스푸핑·조작을 탐지한다.

## 1. NMEA 0183 — 해상 장비 통신 표준

### 정의와 작동 원리
- **NMEA 0183**: 미국 NMEA(National Marine Electronics Association)가 1983년 3월 처음 발표한 **자발적(voluntary) 산업 표준**. 해상 계기 간 통신을 위한 **전기 인터페이스 + 데이터 프로토콜**을 정의한다. (문서 기준 최신은 Version 3.0, 2001-07)
- **장비 역할**: 장비는 **talker(송신)** 또는 **listener(수신)**로 지정되며, 일부는 둘 다 가능. 한 회선에 **talker는 하나, listener는 여러 개** 허용.
- **전기 사양**: 비동기 시리얼, Baud rate **4800**, 데이터 8비트(bit 7=0), stop bit 1+, parity·handshake 없음. talker 출력은 EIA RS-422(차동 A/B 신호) 권장. 신형 **0183-HS(고속)**은 3-wire, **38400 baud**.

### 문장(Sentence) 구조 — 핵심 메커니즘
모든 데이터는 **문장(sentence)** 단위로 전송. 출력 가능 ASCII + CR/LF만 허용.

```javascript
$ttsss,d1,d2,....*hh<CR><LF>
```

| 구성 | 의미 |
| `$` | 문장 시작 (proprietary는 `$P`, query는 5번째 글자 `Q`) |
| `tt` (talker ID) | 송신 장비 종류 2글자 (예: `GP`=GPS, `HC`=자기 컴퍼스, `EC`=ECDIS, `RA`=RADAR/ARPA) |
| `sss` (sentence ID) | 문장 종류 3글자 (예: `GGA`, `RMC`, `VTG`, `HDT`) |
| `,d1,d2,...` | 콤마로 구분된 데이터 필드 (값 없으면 필드는 비우되 콤마는 유지) |
| `*hh` | 체크섬 — `$`와 `*` 사이 모든 문자의 **XOR**을 16진수 2자리로 |
| `<CR><LF>` | 종료 |
- 한 문장은 **최대 80자**(+ `$`, CR/LF).
- **문장 3종류**: talker sentence / proprietary sentence(`$P`+제조사 3글자 ID, 예: Garmin `$PGRM*`) / query sentence(listener가 talker에게 특정 문장 요청).
- 예: `$HCHDM,238,M` → `HC`(자기 컴퍼스) talker가 `HDM`(자기 방위) 문장으로 자기 방위 238도를 보고.

### 우리 IDS와 직결되는 항법 필드
NMEA 문장들이 곧 AIS/항법 데이터의 원천 포맷이다. IDS 피처와 직접 맞닿는 대표 문장:
| 문장 | 담는 값 (IDS 피처와의 연결) |
| `GGA` | 위치(위/경도), UTC, **GPS Quality Indicator**(0=fix없음/1=GPS/2=DGPS), 위성 수, HDOP |
| `RMC` | 최소 권장 항법정보 — 위치, **SOG(knots)**, **track(침로)**, 날짜, 자기편차 |
| `VTG` | **Track Made Good + 대지속력(SOG)** |
| `HDT`/`HDM` | **Heading**(진북/자북) |
| `ROT` | **Rate Of Turn**(°/min, `-`=좌현 선수회전) |
| `GLL` | 위경도 + 데이터 유효성(A/V) |
| `GSA`/`GSV` | DOP·사용 위성, 위성 가시정보(SNR 등) |
→ **우리 프로젝트에서의 의미**: ML 입력 피처(`sog, cog, heading, dist_km` 등)는 모두 이 NMEA 항법 필드에서 유도된다. 체크섬은 *전송 오류*만 잡을 뿐 **출처·진위는 검증 못 하므로**(인증 부재) IDS가 별도로 필요하다.
> 참고: NMEA 2000은 후속 표준으로, **양방향·다중송신·다중수신·자가구성 시리얼 네트워크**(중앙 컨트롤러 없음). 본 도메인에서는 CAN 기반으로 분류된다.

## 2. AIS — 선박 자동 식별 시스템

### 정의·특징
- **AIS(Automatic Identification System)**: 선박 간 및 육상국과의 **자동 위치/상태 정보 교환 시스템**. **VHF 대역** 사용, 충돌 방지·해상 교통 관제 목적.
- **전송 정보**: MMSI(식별번호), 위치(위/경도), **SOG(대지속력)**, **COG(대지침로)**, **Heading**, 선박명, IMO 번호, **항해 상태(NavStatus: 정박/이동 등)**.
- **핵심 특징 3가지** (= 보안 취약점의 근원):
  - **Broadcast 기반 (one-to-many)** — 누구나 수신·송신 가능
  - **암호화 없음**
  - **주기적 송신** — 2~10초 단위(상황에 따라 변동)
→ **우리 프로젝트에서의 의미**: AIS는 **신뢰 기반 시스템**이라 본질적으로 취약. 이 취약성이 IDS 연구를 정당화한다.

### AIVDM 메시지 — AIS의 실제 전송 문자열
AIS 데이터는 내부적으로 binary지만, 실제 전송은 **NMEA 0183 ASCII 문자열**로 변환되며 이때 쓰는 타입이 **AIVDM**.

```javascript
!AIVDM,1,1,,A,15Muq?001oJr>tpE>p4@4?wT0<0u,0*5C
```

| 필드 | 설명 |
| `!AIVDM` | 메시지 타입 |
| `1` | 총 메시지 수 |
| `1` | 현재 메시지 번호 |
| (빈값) | 시퀀스 ID |
| `A` | 채널 (A/B) |
| payload | AIS 데이터 (**6-bit ASCII encoding**) |
| `0` | fill bits |
| `*5C` | 체크섬 |
- payload는 **6-bit ASCII 인코딩** → 디코딩 → binary → **message type(1~27)별 구조 해석** 필요. message type에 따라 필드가 완전히 달라진다.
→ **우리 프로젝트에서의 의미**: AIVDM 문자열이 **실제 공격 surface**다. 문자열(payload) 자체를 조작해 가짜 위치·속도를 주입할 수 있다.

### AIS Spoofing — 우리 IDS의 탐지 대상
AIS 메시지를 조작해 **가짜 선박 정보를 생성/변조**하는 공격.
| 공격 방식 | 내용 |
| **Fake Vessel 생성** | 존재하지 않는 MMSI로 가짜 위치/속도 송신 |
| **Position Spoofing** | 실제 선박 위치 조작 → 항로 이탈처럼 위장 |
| **Replay Attack** | 과거 AIS 메시지 재전송 |
| **Identity Spoofing** | 다른 선박의 MMSI 도용 |
- **근본 원인**: 인증(Authentication) 없음 · 암호화 없음 · Broadcast 구조.
- **영향**: ECDIS에 가짜 선박 표시, 충돌 위험 증가, 관제 트래픽 오분석, 군사 기만 작전 가능.
- **실제 사례**: 유령선(Ghost Ship) 생성, 특정 해역에 수십 척 가짜 선박 표시, 군사·정치적 혼란 유발.
→ **우리 프로젝트에서의 의미**: 이 4가지 공격이 우리 평가 시나리오(32종)가 모사하는 위협이다. IDS는 SOG/COG/Heading/위치 시계열의 물리적 비일관성으로 이를 잡아낸다.

## 3. ECDIS / ECS / OpenCPN — 표시·통합 계층

### ECDIS (Electronic Chart Display and Information System)
- 전자 해도 기반으로 항해 정보를 **통합 표시**하는 시스템. **AIS·GPS·Radar** 등 다양한 센서 데이터를 통합.
- 기능: 실시간 선박 위치 표시, 항로 계획·안내, 위험 경고(충돌·좌초), 주변 선박(AIS) 표시.
- **IMO 규격 준수 시 종이 해도를 법적으로 대체** 가능 — 브리지(bridge)의 중심 항해 시스템.

### ECS (Electronic Chart System)
ECDIS와 유사하나 **표준 인증이 없는** 시스템.
| 구분 | ECDIS | ECS |
| 표준 준수 | IMO/IHO 준수 | 비표준 |
| 법적 인정 | 가능(종이 해도 대체) | 불가능 |
| 사용 데이터 | **ENC**(공식 전자해도) | 비공식 해도 가능 |
| 용도 | 상선 필수 장비 | 보조 장비 |

### OpenCPN — 우리 플러그인의 호스트
오픈소스 항해 SW(ECS 계열). 우리 C++ 플러그인이 여기에 붙는다.
- **플러그인 API**: 항법 데이터는 `PlugIn_AIS_Target` 구조체로 접근. 주요 멤버:
  - `MMSI`(식별번호), `Class`(Class A:0 / Class B:1), `NavStatus`(0~15)
  - `SOG`(knots), `COG`/`HDG`(degrees true), `Lon`/`Lat`(십진도), `ROTAIS`
  - `ShipType`(ITU-R M.1371 기준), `IMO`, `CallSign`, `ShipName`
  - 충돌 파라미터: `bCPA_Valid`, `TCPA`(최근접점까지 시간, 분), `CPA`(최근접거리, NM), `alarm_state`
- **로그**: `wxLogMessage(...)` → `~/.opencpn/opencpn.log`에 출력.
- **리눅스 플러그인 경로**: `~/.local/lib/opencpn/`(라이브러리), `~/.local/share/opencpn/plugins/<plugin>/`(데이터 파일).
- **빌드 의존**: `opencpn-libs`는 git 서브모듈 — 첫 빌드 전 `git submodule update --init --recursive`.
→ **우리 프로젝트에서의 의미**: `PlugIn_AIS_Target`이 IDS의 **입력 게이트웨이**. 이 구조체 필드(SOG/COG/HDG/Lat/Lon/NavStatus)가 그대로 ML 피처가 되며, `ML_FEATURE_COUNT`는 배포 모델과 정확히 일치해야 한다.

## 4. 해도 데이터 표준 — ENC / S-57 / S-63
| 표준 | 정의·역할 (출처 근거 범위 내) |
| **ENC** | Electronic Navigational Chart — 공식 전자해도. ECDIS의 데이터 기반. 항해 안전의 필수 요소. |
| **S-57** | IHO(국제수로기구)가 정한 **ENC 데이터 형식 표준**. ECDIS가 사용하는 해도 데이터 포맷. |
| **S-63** | S-57 ENC를 **보호**하기 위한 데이터 보호 표준(Edition 1.2.1, 2017). **Blowfish 기반 암호화 + 디지털 서명 + 해시 검증**으로 위·변조 방지. |
> 본 소스들은 S-100/S-52를 별도 정의하지 않는다. 확인된 사실은 위 ENC/S-57/S-63 체계와, **S-63은 "데이터 자체"의 무결성만 보호하고 "운용 절차"(예: 차트 삭제)는 다루지 않는다**는 점이다.

### Edition 0(삭제형 업데이트) 오용 — 절차적 공격면
- **Edition 0**: 차트를 구버전으로 간주할 때 Edition 번호를 `0`으로 설정해 **해당 차트를 해도 목록에서 제거**하는 삭제형 갱신(Transas Navi-Sailor 3000 ECDIS 실제 기능).
- **취약점**: 사용자 단순 확인(`Yes` 클릭)만으로 삭제 완료. **별도 검증 절차 없음** → 실수·악의 모두에 취약.
- **오남용 시나리오 3종**: ① 항해 중 실수 클릭으로 항로상 차트 삭제, ② USB/네트워크로 **위조 Edition 0 삽입 → Chart DoS** 공격, ③ 자동 스케줄러와 충돌해 무확인 자동 삭제.
- **사례**: MAIB(영국 해양사고조사국) Kaami 좌초 보고서 — ENC 셀 미적재 + 안전설정 오류로 좌초. **절차적 결함이 중대 사고로** 이어짐을 입증.
- **제안 대응**: 하드웨어 변경 없는 경량 **Safe-Delete SOP**(5단계: 대상 목록 확인 → 항로 공백 검토 → 관리자 이중 승인 → 백업 확인 → 삭제 후 로그/보고). 향후 로그 기반 위협 탐지 연계 가능.
→ **우리 프로젝트에서의 의미**: AIS 스푸핑이 "데이터 위조"라면 Edition 0은 "데이터 삭제(가용성)" 공격. 해상 시스템 위협이 **암호화 외에 절차·운용 사각지대**에도 존재함을 보여주며, 로그 기반 탐지가 IDS의 잠재 확장점임을 시사한다.

## 5. 해상 네트워크 vs SCADA — 우리 IDS 설계 제약의 근거
우리 IDS는 육상 SCADA에서 검증된 IDS를 해상에 이식하려는 흐름의 연장선이다. 비교 연구가 도출한 차이가 곧 설계 제약이다.
| 항목 | SCADA(육상 산업제어망) | 해상 네트워크 |
| 망 구조 | 폐쇄형·고정망, 외부 접근 제한 | **개방형·이동형**, 외부 침입 위험 높음 |
| 프로토콜 | **Modbus, DNP3**(표준) | **NMEA, IEC 61162-450, AIS, VDES, GMDSS**  • 커스텀(비표준 혼재) |
| 보안 기능 | 인증·무결성 일부 적용 | **대부분 평문** → 변조·위·변조·재전송에 취약 |
| 운영 환경 | 고정·안정 → 실시간 IDS 용이 | 이동성·위성 지연 → 실시간/중앙집중 IDS 어려움 |
| 데이터 | 라벨·정상로그 확보 용이 | 정상 로그 부족, 공격 라벨 부재, 환경변화로 drift |

### IDS 기법별 한계 (소스 정리)
- **시그니처 기반**(Snort/Suricata): 알려진 공격엔 효과적이나 규칙 갱신 부담.
- **프로토콜 인식형**: 제조사 확장·비표준 메시지로 정확도 저하, 규칙 개발 난이도↑.
- **이상 탐지형**: 미지 공격에 유리하나 정상/비정상 로그 확보 곤란, **drift**로 장기 성능 저하.
- **ML 기반**: **LSTM-Autoencoder, 1D CNN** 시계열 이상탐지. 정상 패턴 학습 후 **재구성 오차(Reconstruction Error)가 임곗값 초과 시 이상 분류**. NMEA·CAN처럼 **주기적·결정적(deterministic)** 트래픽에 적합.

### 해상 적용 시 고려 요소 (설계 원칙)
- 프로토콜 호환성(ASCII NMEA + CAN 혼합 → 파서 통합 어려움)
- 대역폭 제약(위성) → **이벤트 기반 전송** 구조 필요
- 운항 환경 변동(기상·항로 변경으로 정상 패턴 변동) → **동적 임곗값 조정** 필요
- 운영 인력 한계(전담 보안 인력 부족) → **경량·직관적** 설계 필요
- 결론적 설계 원칙: **경량화 · 분산화 · 프로토콜 적응성**
→ **우리 프로젝트에서의 의미**: 우리 시스템이 **DCdetect/재구성 오차+임곗값** 방식을 쓰는 것, **FP=1%(99퍼센타일) 임곗값**으로 오탐을 관리하는 것, 경량 ONNX 모델을 OpenCPN 플러그인에 내장하는 것이 모두 이 "경량·적응형·결정적 트래픽" 요구와 정합한다. 정상 로그 부족·drift는 시나리오 기반 합성 공격 평가(32종)와 동적 임곗값으로 보완하는 방향과 연결된다.
