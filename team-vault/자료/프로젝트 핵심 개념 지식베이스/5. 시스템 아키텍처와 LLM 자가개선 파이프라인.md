# 5. 시스템 아키텍처와 LLM 자가개선 파이프라인

## 1. 프로젝트 목표와 범위 (사업계획서)

### 핵심 정의
- **목표**: 선박에서 수신한 **AIS** 신호 기반 공격을 분석·탐지하는 **AIS 기반 IDS** 설계·구현.
- **탐지 대상 이상 행위**: 스푸핑(Spoofing), Ghost Ship(유령 선박), Flooding(대량 송신), 위치 위·변조(Position Manipulation).
- **구현 언어**: Python 중심 — `수신 → 파싱 → 탐지 → 사용자 알림` 흐름.
- **최종 산출물**: ① Python 기반 AIS IDS 엔진 ② 관련 논문. **확장 산출물**: OpenCPN 호환 플러그인.
→ 의미: 사업계획서 단계의 "확장 가능성"이던 OpenCPN 플러그인이 실제 메인 배포 형태(`ais_ids_pi`)로 자리잡았다.

### AIS의 구조적 취약점
| 특성 | 보안 함의 |
| **인증 없음** | 송신자가 누구인지 검증 불가 |
| **암호화 없음** | 내용 위·변조 탐지 불가 |
| **브로드캐스트 기반** | 누구나 수신·송신 가능 |
⇒ 구조적으로 수신자가 **무조건적 신뢰를 가정**할 수밖에 없는 취약점이 내재. 이 신뢰 가정의 빈틈을 IDS가 메운다.

### 규칙 기반 탐지 임계값 예시 (계획서)
- 동일 MMSI **1초 50개 이상** → Flooding
- 동일 MMSI **10초 내 10km 이동** → Spoofing
- 속도 **> 100노트(≈200km/h)** → 비정상 속도 (통상 최대 30노트 ≈ 55km/h)
- 일정 면적 내 과도하게 많은 선박 수 → 이상
→ 의미: 이 정량 규칙들이 이후 ML 파생 피처(ΔTime, ΔDistance, Calculated Speed, MMSI Frequency, Heading Variation)와 평가 시나리오(Basic/FN 그룹)의 출발점이 됐다.

## 2. AIS 신호 처리 구조와 Snort 형식 엔진 아이디어

### AIS 메시지 변환 파이프라인

```javascript
VHF AIS 신호 (초단파)
  ⇒ AIS Binary Message (ITU-R M.1371)
  ⇒ NMEA sentence (!AIVDM)
  ⇒ Decoder (AIS parser, 예: pyais)
  ⇒ JSON / CSV 데이터셋
```

**AIVDM 문장 포맷**:

```javascript
!AIVDM,<fragment count>,<fragment number>,<msg id>,<channel>,<payload>,<fill bits>*<checksum>
예) !AIVDM,1,1,,A,177KQJ5000G?tO`K>RA1wUbN0TKH,0*5C
```

디코딩 후 JSON 필드 예: `MMSI, TSTAMP, LATITUDE, LONGITUDE, COG, SOG, HEADING, NAVSTAT, ...`
→ 의미: 이 디코딩 JSON 필드가 ML 입력 피처(sog, cog, heading, status=NAVSTAT 등)의 원천이다.

### Snort 형식 엔진 아이디어
- IDS 규칙 엔진의 사실상 표준인 **Snort**(과 Suricata)의 **rule header + option** 형식을 AIS 신호 탐지에 차용하려는 구상.
- 즉, 네트워크 패킷 룰처럼 **AIS 신호에 대한 시그니처/규칙 형식**으로 이상 패턴을 기술하는 엔진(2주차 조사 단계).
→ 의미: 규칙 기반(Snort 스타일) 탐지와 비지도 ML(DCdetect) 탐지를 **상호 보완**하는 이중 트랙의 출발점. 평가 시나리오 중 FN 그룹이 "규칙 기반 탐지기 회피용"으로 설계된 것도 이 맥락이다.

## 3. OpenCPN 플러그인 (ais_ids_pi) — 배포 형태와 빌드 환경

### 위치
실시간 탐지는 오픈소스 ECS인 **OpenCPN**의 플러그인(`ais_ids_pi`)으로 동작한다. AIS 메시지(AIVDM)를 12개 피처로 추출 → ONNX 모델 추론 → 정상/이상(anomaly score) 판정.

### 개발 환경 (native Linux)
- **OS**: VirtualBox 우분투 **24.04 LTS**.
- **OpenCPN**: 5.13.2 (PPA `ppa:opencpn/opencpn`으로 설치).
- **플러그인 빌드 종속성**: `cmake, libwxgtk3.2-dev, gettext, libbz2-dev, libzip-dev, devscripts, equivs` + `mk-build-deps -i -r ci/control`.
- **AIVDM 생성기 종속성**: `python3, python3-tk`.
→ 의미: 플러그인 빌드/배포는 **네이티브 Linux(Ubuntu 24.04)** 전용. Windows는 ML 모델 학습에만 사용한다.

### 배포 파일 (3종 세트)
모델은 `model_{name}.onnx` + `scaler_{name}.json` + `threshold_{name}.txt` 3파일로 산출되어 플러그인의 `ais_ids_pi/data/`로 배포된다(ONNX 런타임 추론).

## 4. LLM이 운영하는 자가개선 MLOps 파이프라인 (핵심 방법론)
발표 서사의 한 줄 메시지: **"우리는 모델 하나를 학습시킨 게 아니라, LLM이 개발·분석·판단·피처발명하는 자가개선 MLOps 파이프라인을 설계했다."** 대부분의 학부 연구가 "모델 만들고 정확도 보고"에서 끝나는 데 반해, 성과의 본체는 **파이프라인 그 자체**다.

### 4.1 LLM 4중 활용 (전부 실제 구현·동작)
| # | 역할 | 구현 | 하는 일 |
| 1 | **개발자** | Claude Code + `CLAUDE.md` 컨텍스트 | ml/ 파이프라인 전체(전처리·9모델 벤치마크·평가·FE·오케스트레이터)를 LLM이 작성 |
| 2 | **분석가** | `claude_analyze` (pipeline_[steps.py](http://steps.py/)) | 매 단계 결과를 5섹션으로 상세 분석(탐지율 해석·채택피처 물리해석·약세 진단·다음 전략·판정) |
| 3 | **심판 (LLM-as-judge)** | `claude_harness` ([orchestrator.py](http://orchestrator.py/)) | 각 노드 뒤 JSON verdict `{assessment, evidence, verdict: continue |
| 4 | **피처 엔지니어** | `n_recommend` / reco 노드 | 약세 시나리오를 읽고 **새 파생피처를 발명**(lambda 코드 생성)→더미 검증→후보풀 확장 |
**정직성 가드(핵심 원칙)**: LLM은 **제안**하고, **채택은 데이터가 결정**한다 — 목적점수 **+3.0pp** 게이트를 통과한 피처만 채택. 즉 무비판적 LLM 신뢰가 아니라 **LLM 자동화 + 정량 검증 하이브리드**.

### 4.2 세 기둥 — 위키 / LangGraph / MCP
단순 챗봇과의 본질 차이: **LLM이 "조언자"가 아니라 "행위자(agent)"**다. "관측→판단→행동→기록"하는 자율 작업자.
| 구분 | 단순 챗봇 (ChatGPT 대화) | 우리 방식 |
| 입력 | 사람이 매번 프롬프트 타이핑 | 파이프라인 상태·로그·시트·git이 자동 주입 |
| 출력 | 사람이 읽는 텍스트 | 구조화 JSON verdict → 코드가 다음 동작 분기 |
| 도구 | 없음(말만) | MCP로 git·Slack·Sheets·Notion·파일 직접 조작 |
| 기억 | 세션 끝나면 소멸 | 위키·Obsidian·체크포인트에 영속 |
| 검증 | 사람이 눈으로 | 정량 게이트(+3.0pp)·더미 실행·LLM-as-judge |
| 반복 | 1회성 Q&A | LangGraph 사이클로 수렴까지 자동 반복 |
**(1) LLM 위키 — 검증 가능한 지식 기반**: 노션(SSOT) → git(`team-vault/`) → 팀원 Obsidian으로 매일 자동 미러되는 단방향 지식베이스. PDF/DOCX는 markdown으로 자동 변환. 단순 저장소가 아니라 **LLM이 작업 시작 시 읽는 컨텍스트 원천**. 사람과 LLM이 같은 진실(SSOT)을 봐서 "옛 정보로 헛소리"를 구조적으로 차단.
**(2) LangGraph — LLM을 상태기계로**: 파이프라인을 **노드(작업)+엣지(흐름)의 그래프(StateGraph)**로 표현. 분기·사이클·중단/재개 가능. 핵심: 노드 / 조건엣지(`verdict` 분기) / **사이클**(브랜치 체이닝 = 자동 반복) / **`interrupt()`**(멈췄다 사람 승인 후 재개, HITL) / 체크포인터. 적용처: ① ML 오케스트레이터 ② 야간 운영봇 `ops_graph.py`(6개 헬스체크 노드 병렬 → 집계 → 조건분기).
**(3) MCP(Model Context Protocol) — LLM에게 손 달아주기**: LLM이 외부 도구/서비스를 **표준 규약으로 직접 호출**. 붙인 MCP: GitHub, Google Sheets, Notion, Slack, Obsidian, 파일시스템, 시퀀셜씽킹 등. 챗봇은 "이 명령을 실행하세요" 안내만 하지만, MCP 에이전트는 **그 명령을 자기가 실행**하고 결과를 확인한다.

### 4.3 파이프라인 아키텍처 (LangGraph StateGraph)

```javascript
        ┌────────── 브랜치 체이닝 (그래프 사이클) ──────────┐
        ↓                                                   │
new_branch → baseline →[reco: LLM 피처발명]→ fe_train →[게이트:사람승인]→ release → chain
        │하네스           │하네스             │하네스                         │하네스
        └─ claude_harness verdict (continue/retry/stop) ────────────────┘
                                수렴 시 → converge → END
```

- **interrupt() HITL 게이트**: 배포·릴리스 같은 비가역 단계는 **사람이 최종 승인**(LLM 분석은 의사결정 보조).
- **자동화 백본**: Slack 실시간 보고 + Google Sheets 5탭 기록 + git 브랜치/커밋/GitHub 릴리즈 자동.
- **체크포인트(MemorySaver)**: 중단→재개 가능.

### 4.4 셋이 합쳐진 자가개선 루프

```javascript
[위키/SSOT] ──읽기──▶ [LangGraph 노드: LLM 호출] ──MCP──▶ [git/Sheets/Slack/Notion 조작]
     ▲                       │ verdict(JSON)                     │
     │                       ▼ 조건분기                          │
     └──────────  [결과를 위키·시트에 기록] ◀────────────────┘
                  (다음 LLM 호출의 컨텍스트가 됨 = 학습 루프)
```

1. LLM이 위키/상태를 읽어 맥락 파악(백지 아님) → 2. LangGraph 노드에서 분석·판단 → 3. MCP로 실제 행동 → 4. 결과를 위키/시트에 기록 → 다음 사이클 입력 = **자가개선 루프**.
→ 의미: 사람이 일일이 피처를 깎는 대신, LLM 4역할 + 정량 게이트 + 사람 승인이 맞물려 탐지율을 자동으로 끌어올린다.

## 5. 파이프라인이 만든 결과 (수치)
- 베이스 **12피처 FP=1% 40.6%** → 자동 Greedy FE → **20피처 91.9%** (FP=5% 97.6% / FP=10% 98.7%). ← 공식 freeze 수치(Iter8).
- run마다 LLM 분석 → 1피처 자동 채택 → 재학습 → 배포까지 사람 개입 최소화.
- **32개 공격 시나리오** 평가 자동화(정상↔이상 시퀀스 생성 → 탐지율/오탐율).

### 발표용 정직성 가드 (반드시 지킬 선)
1. LLM이 발명한 피처도 **정량 게이트(+3.0pp) 통과분만 채택**.
1. 최종 배포는 **사람이 승인**(interrupt 게이트) — 완전 무인 맹신 아님.
1. **수치는 freeze 값만 인용**(Iter8 20피처 91.9%). 구 83.5%/최신 84.1%는 평가조건이 달라 미사용.
1. 데모는 **녹화 백업 필수**(라이브 실패 대비).
→ 의미: 발표의 주인공은 "모델"이 아니라 "**파이프라인 방법론**"이며, 수치 인용 시 freeze 값(91.9%)만 사용한다.
